代码不再是瓶颈

组织已经开始以一年前难以想象的速度使用 AI 编写代码，但围绕代码的流程却没能以同样的速度改变。

许多工程团队仍然沿用同样的审批关卡、评审流程、交接环节和策略，从而拖慢了使用 Claude Code 这类智能体编码方案所取得的效率提升。

软件开发生命周期（SDLC）是把软件从想法推进到生产的流程。大多数组织都在运行某种版本的同一套六个阶段，覆盖软件的规划、设计、构建、测试、部署和维护。传统上，每个阶段都是一个独立的阶段，由不同的角色负责。产品经理编写需求，技术架构师把需求转成设计，工程师落地设计，受监管企业中的 QA 团队负责验证，发布团队负责上线，运维团队监控正在运行的系统。工作通过文档、工单和审批签字在各个阶段之间流转。

传统的软件开发生命周期（SDLC）流程繁重，是为了在每个环节确保责任可追、受控可控。然而，传统 SDLC 的设计初衷是在一个"编写并实现代码"是最耗时、最昂贵的阶段的时代里实现效率最大化，而如今情况已不再如此。PRD（产品需求文档）、工期估算仪式、产品安全评审——所有这些之所以存在，都是为了在可能是数周、数月甚至数季度的开发工作期间强制各方保持一致。

传统 SDLC 还带有一些默认假设"每一步都由人类执行"的控制手段。而那些创造最大价值的组织，已经围绕智能体 AI 如今能够做到的事情重建了它们的流程，同时确保人类始终在环（human in the loop）。在本指南中，我们梳理了 Applied AI 团队在 SDLC 各个阶段内部集成 Claude 的若干最佳实践，以加速开发、让流程跑得更快——这些实践源自我们与客户合作的经验。

当代码不再是瓶颈、构建阶段比传统 SDLC 所允许的速度更快时，有三件事会变成现实：

  • 瓶颈转移到了构建阶段左右两侧的环节上。这主要是规划、评审/测试和部署，它们仍然以人类的速度运行。
  • 控制手段不再与现实匹配，变得难以实施。当代码由某个人编写时，逐行人工评审是合理的；可一旦大部分 diff（变更）由智能体写出，人工评审就跟不上了。
  • 治理成本上升，因为例外情况仍然要经过每周或每月召开一次的会议和委员会来流转。

让我们以安全瓶颈为例。安全团队的人力是按人类产出规模配置的，因此当智能体成倍地增加代码产出时，要么评审队列越积越长，要么代码在评审不足的情况下上线。受监管的组织无法接受这两种结果，所以它们的安全与策略检查必须跟上智能体的节奏。

为了更好地实现智能体 AI 的生产力提升并为其提供安全保障，传统 SDLC 生命周期需要经历与实现阶段所经历的那样的同等程度的转型。

什么是 AI 原生的 SDLC？

AI 原生 SDLC 是一种重新构想的流程，它把旧有的控制目标与新的执行机制结合起来。它不再是线性的流程，而是变成了一个循环，并且 AI 被嵌入到每一个节点。AI 原生 SDLC 促进了自动化交接以及后续行动的自动触发，有助于解决传统 SDLC 各阶段之间交接那种手动、笨拙的特性。

你也会听到这种转变被称为智能体式 SDLC（agentic SDLC）、AI SDLC，或者干脆叫智能体式软件开发（agentic software development）——叫法不同，但描述的是同一件事。

AI 原生 SDLC 六个阶段的转变

下表突出显示了由 Claude 支撑的传统 SDLC 与 AI 原生 SDLC 之间的两个端点。大多数组织介于这两列之间。

阶段传统 SDLCAI 原生 SDLC
规划 需求由委员会收集，经工作坊与签字提炼，再手工整理成文 Claude 直接从源头综合痛点，并将其捕获到 intent.md 中——该文件既可供人阅读，又可被机器执行
设计 规格由分析师编写，再由设计师解析 需求与设计在同一个工作会话中由智能体压缩完成，并由以技能（skills）编码、在 git 中版本化的标准来指导
构建 测试与代码手工编写，文档在主开发之后才补写 测试与代码由 AI 生成，机构知识以版本化的、机器可读的 CLAUDE.md 文件与技能来维护
测试 QA 关卡设在阶段边界处 持续的评估（evals）编织在整个实现过程之中
部署 人类逐行评审所有代码，治理发生在评审周期中，且往往执行不一致 多层智能体评审，人类评审只保留给受监管的和关键性的代码。治理在 AI 行动时即时执行，钩子（hooks）作为审批关卡
维护 人类盯着生产环境找 bug 智能体监控线上部署。任何被突破的控制带（control band）都会被诊断，并作为新的 intent.md 写回循环中

贯穿右栏的一条主线是"已提交的产物"（committed artifact）。每个阶段结束时都会把一个产物写入版本控制（包括 intent.md、spec.md、plan.md、diff 及其测试、带有评审结论的 PR、以及事故记录），而下一阶段则以读取它作为开始。对于早期阶段，.md 文件是主要的产物，因为产品负责人和智能体都能阅读并操作同一个文件。从构建阶段往后，产物就是代码及其记录。提交链同时也是审计线索：谁要求了什么、智能体产出了什么、谁批准了它。

人类仍然对每一个需要判断力的决策负责。在智能体式 SDLC 的世界里，人类的注意力随着那些必须被评审的产物一起转移。

每个阶段都会提交一个可供下一阶段读取的产物。意图、规格、计划、diff 与评审结论合在一起，就是审计线索。

行动（Plays）

这些行动是这本手册的核心，被归入六个非线性的阶段（规划、设计、构建、测试、部署、维护），它们共同覆盖了完整的生命周期。

每项行动都涵盖：

  • 改变了什么；
  • 如何开始；
  • 具体的实施步骤；
  • 治理考量；以及
  • 如何衡量它是否奏效。

这些步骤是模块化的，组织可以根据自身的独特需求，在不同时间优先改造不同的阶段。每项行动都会在"前置条件"（Prerequisites）下列出它的依赖项，依赖关系图会进一步说明这些关系。

一个阶段以提交一个产物而结束，而该提交又会触发下一个阶段。一份被接受的 intent.md 会触发需求与设计环节，一份获批的 spec.md 会触发计划模式，一个被合并的 PR 会触发流水线，而生产环境中的一个被突破的控制带则会写出下一个 intent.md——于是循环就这样继续下去。

首先，你手工提示每一个步骤，其最终状态是一个循环：每个被接受的产物都会触发下一个关卡。人类的注意力集中在这些关卡上，评审智能体标记出来的内容，而不是从头开始每个阶段。

01规划（Plan）

想法不再需要等待某个人去把它写下来。意图只被捕获一次，用提出者自己的话，作为一个可版本化的产物，供下一阶段操作。

以 intent.md 捕获

启动软件开发流程的 intent.md 可以通过不同的途径进入。某个人有了想法，提交了一个工单，或者某个告警暴露了一起事故（见阶段 6：维护）。

当某个人有想法时，他会与 Claude 进行头脑风暴，并产出一份 markdown 原型规格（proto-spec）。在传统 SDLC 中，同一个人还必须说服产品团队的一名成员，和他一起或替他写下这个想法。

由 Claude 生成的原型规格可被人阅读、可版本化，并且能立即被下一阶段消费。原型规格被保存为 intent.md。

无论意图来自事件触发器还是智能体，所应用的步骤都是一样的：产品负责人在提交 intent.md 之前，先评审并纠正由智能体写出的这份文件。

传统

一个想法必须先经过积压条目、用户故事、故事点以及细化会议，才能有人对其采取行动。所有权在每次交接时转移，因此最终到达工程团队的内容，与提出者最初的意思已经隔了好几层。

AI 原生

提出者与 Claude 头脑风暴，并把结果以 intent.md 的形式写下来——这是用提出者自己的语言写成的原型规格。该产物包含想要什么、为什么，以及在哪些约束之下。重复的流程通过技能（skills）来编码。

如何开始

前置条件

无。

基础设施

为非工程师人员提供 Claude 访问权限（claude.ai 或 Cowork）；一份双方认可的 intent.md 模板；一个共享的、可版本化的意图存放处，由产品负责人盯着。对单一产品而言，最简单的存放处是产品仓库里的一个 intent/ 文件夹。这样的设置能让产物链紧邻由其派生的代码。只有当意图横跨多个仓库时，才值得为它单独建一个意图仓库；在单体仓库（monorepo）中，它就是一个目录。阶段 3：构建的侧栏会说明这个存放处与已经持有记录的 Jira 或需求工具之间的关系。

搭建这个环境对平台团队或工程团队来说是一次性任务。需要一名技术人员来搭起意图存放处，并决定谁能写入它，因为很多贡献者将来自组织的各个部门。

一旦仓库存在，没有 git 经验的贡献者就不必直接使用 git。取而代之的是，一个到版本控制系统（例如 GitHub）的连接器，让 Claude 能代表他们从 claude.ai 或 Cowork 提交 markdown 文件。

如何执行

  1. 提出者用自己的话向 Claude 描述问题。提出者可以描述今天他们做不到什么、这个想法影响谁、更好是什么样的、或者哪些属于范围之外。不需要任何正式语言。
  2. 头脑风暴，直到想法变得具体。Claude 会问分析师会问的那些问题：范围、用户、约束，以及成功是什么样子。
  3. 让 Claude 使用组织的模板把结果写成 intent.md。该模板可以被编码成一套由技术团队成员搭建、并经负责人签署的技能。它可以涵盖问题、拟议结果、受影响的用户与系统、约束以及未决问题。
  4. 提出者纠正任何 Claude 误解的地方。
  5. 把 intent.md 提交到共享存放处。作者和时间戳加入记录，产品负责人从那里接手这个想法。
示例（intent.md）
# 意图：理赔状态自助服务
作者：J. Ortiz（理赔运营）。状态：草稿。

## 问题
客户打电话到联络中心询问他们的理赔进行到哪一步了。
坐席人员把约三分之一的通话时间花在了仅查询状态的请求上。

## 拟议结果
客户可以在门户中看到理赔状态、下一步操作和预计日期。

## 受影响的用户与系统
理赔坐席人员、门户团队、claims-core API。

## 约束
门户会话中不新增任何 PII。仅使用现有的身份验证。

## 未决问题
第三方损失理算人是否也需要访问权限？

治理考量

证据就是已提交的 intent.md，它列明了作者、时间戳和完整的修订历史。它记录在意图存放处的 git 历史中。产品负责人负责批准，而把意图送入阶段 2：设计的接受或拒绝决定，则记录为合并操作或关闭评审。

如何衡量

先行指标：从第一次对话到提交 intent.md 的时间，从意图存放处的 git 历史读取，它记录了作者和时间戳。预期是从一个长达数周的引出与细化周期，缩短到数小时。

滞后指标：存活率，即产品负责人接受进入阶段 2：设计、而非关闭的 intent.md 文件的占比。接受或拒绝的决定记录为产物的合并或关闭评审。此外，还有在同一变更的第一个 spec.md 提交之后，对 intent.md 所做的修改次数。

02设计（Design）

需求与设计合并为一次会话。策略在编写规格时就已应用，而不是在数周后的评审中才发现。

需求与设计

一旦获得产品负责人批准，Claude 就会接手被接受的 intent.md，产出一份需求与设计规格。这由组织针对品牌、安全、合规和用户体验的技能（skills）来指导。

产品负责人评审这份规格，但不编写它。这个过程的目标是创建一份工程团队可以据此规划的规格，并标记出值得关注的区域。

前端工作是最清晰的例子。一旦 intent.md 被接受，产品负责人就会基于 intent.md 在 Claude Design（测试版）中制作设计稿，迭代打磨，然后将其导出到 Claude Code 去构建。

传统

需求与设计是由不同团队运行的两个独立阶段。分析师把想法正式化为需求，设计师再把需求解析回设计。这种分离是为了问责，但它既慢又会有信息损耗。

AI 原生

两个阶段都发生在同一次提示会话中。Claude 接受 intent.md，产出一份需求与设计规格，受组织技能的约束，并标记出值得关注的区域。

如何开始

前置条件

写一份 intent.md 文件，并把品牌、安全、合规与用户体验策略写成技能。

基础设施

一名有 Claude 访问权限的产品负责人。不需要任何工程技能。

如何执行

  1. 产品负责人打开一个带有组织技能可用、并附上 intent.md 的会话。
  2. 产品负责人的提示指向 intent.md，点名约束，并要求标记关注点。一开始手工运行，然后把它固化为组织级的斜杠命令。从这里开始，把意图存放处中 intent.md 的接受设为触发器，用一个在合并时触发的非交互式任务，加载组织的技能运行该环节，并把 spec.md 作为拉取请求（PR）提交（阶段 5：部署中的 CI/CD 行动涵盖相关管道）。从那一刻起，产品负责人的第一次介入就是评审。
  3. 同一位产品负责人对照这个想法评审这份规格。这份规格是否解决了所述的问题？intent.md 中的未决问题是得到了回答，还是被带入了后续？
  4. 首先处理被标记的关注点，因为它们正是分析师会升级处理的地方。产品负责人在工程团队看到规格之前，与每个关注点的策略负责人一起解决它们。
  5. 把 spec.md 与 intent.md 一起提交。这对文件记录了要求了什么、决定了什么。
  6. 产品负责人决定规格与意图是否进入构建，并针对组织归类为较高风险的事项咨询技术负责人。这个判断始终由一名人类队友做出，而接受规格正是启动阶段 3：构建中计划模式行动的东西。
它长什么样（提示词）
阅读所附的 intent.md，产出一份把它集成到我们现有代码库中的需求与设计规格。
应用你可用到的技能，使计划符合我们的品牌指南、安全策略与用户体验标准。
把规格完整地记录为 spec.md，准备交给工程团队。
清晰描述任何值得关注的区域，尤其是你无法满足相互冲突的策略的地方。

治理考量

实时的策略不是数周后的评审中才被发现，而是在编写规格的同时就被读取和应用。组织的技能作为规格上的约束被应用。规格、生成它的提示词，以及生效中的技能版本，全部记录在版本控制中。产品负责人签署规格，并把被标记的关注点转给指定的策略负责人。

如何衡量

先行指标：同一变更的 intent.md 提交与 spec.md 提交之间的耗时（两个 git 时间戳），与旧的需求加设计周期相比。

滞后指标：构建开始后的需求返工。统计同一变更的第一个 plan.md 提交之后、日期晚于它的 spec.md 提交数。git 日志会直接给出这一点。

03构建（Build）

没有一份被接受的计划，就不会实现任何东西。机构知识变成了智能体读取的文件，护栏以代码而非习惯的方式运行。

将 Claude Code 的计划模式作为默认起点

工程师以计划模式启动 Claude Code 会话，把阶段 2：设计中获批的 spec.md 交给 Claude，让它采访他们，迭代计划，直到工程师满意为止。

传统

工程师阅读设计然后开始写代码。变更将如何进行——细化到改哪些文件、哪些测试——停留在工程师的脑子里，最好也不过是工单里的一条评论。没有其他人能评审它。评审者看到的第一样东西是完成的 diff，而到那时返工已经很慢了。

AI 原生

工作始于 Claude 在计划模式中产出的书面计划——在这种模式下它可以读取代码库而不改动任何东西。工程师在写代码之前纠正计划，获批的版本作为 plan.md 提交，供后续阶段对照检查。

如何开始

前置条件

如果存在意图产物（intent.md 或 spec.md），以及 CLAUDE.md 文件，会有帮助。

基础设施

能够访问仓库的 Claude Code。

如何执行

  1. 工程师以计划模式与 Claude 启动会话。
  2. 工程师把 intent.md 和 spec.md 交给 Claude，要求给出一个实施计划，点名要改的文件、工作的顺序，以及能证明其正确的测试。
  3. 通过追问来拷问这份计划：这个变更可能破坏什么？哪一步风险最高？Claude 选择不去做的其他选项是什么？
  4. 迭代，直到一个从未看过这段对话的工程师也能仅凭这份计划就实现该变更。
  5. 把获批的计划提交为 plan.md。计划加入审计线索，PR 评审行动（阶段 5：部署）会对照它检查最终的 diff。
  6. 接受计划，让 Claude 实现。有了扎实的计划，实现往往一次就完成。

Claude Code 的自动模式

Claude Code 也可以运行在自动模式下：工程师批准计划，一旦满意并迭代完成，Claude 就在没有逐次编辑提示的情况下应用每一个变更。随着后面各行动中的护栏逐渐成熟（一份调优的 CLAUDE.md、编码策略的技能、阻止不安全动作的钩子，以及 Claude 可以运行的测试套件），自动接受会成为常规工作的默认：一份紧凑的 spec.md、很小的爆炸半径，以及已经被测试覆盖的代码。

现在的转变是：从用户盯着智能体做编辑、评审每一个动作，转向在更长的自主会话之后评审产物。自动接受模式在使用工作树（worktrees）时，还能进一步实现个人与团队层面的并行，并且是自主运行 SDLC、按阶段 6：维护中描述的方式闭环的基础。

侧栏

遗留系统与真相之源

适用于流程产出的每一个产物。

现有的 SDLC 流程可能已经在追踪产物了，只是用的不是 markdown 文件。工作项可能在 Jira 里，需求在某个内置了监管可追溯性的工具里，设计在 Figma 里，变更审批在变更委员会那里。这些系统很难被取代，因为审计人员和监管机构已经接受了它们，而且其他团队也依赖它们，所以 AI 原生 SDLC 必须适配既有的环境。

在向 AI 原生 SDLC 过渡时，对于流程产出的每一个产物，指定一个系统作为真相之源，其余一切只保留副本或指向原件的链接。可以按下面的配置设置单一真相之源，不同产物的选择不同：

  • 以仓库为真相之源。markdown 产物是权威记录，遗留系统引用提交内的文件。对由工程主导的组织来说，这可能是一种最干净的配置，因为所有记录都在一个工具中、只有一个时间戳权威。
  • 以遗留系统为真相之源。Jira、ServiceNow 或需求工具持有权威记录，markdown 产物是工作副本。Claude 在会话开始时读取记录，并在同一个产生规格或计划的会话中，通过 MCP 连接器把结果写回。
  • 以链接为最低标准。所有产物都标注记录 ID，所有遗留记录都包含 markdown 文件的提交 SHA。在向 AI 原生 SDLC 过渡时，链接是一个好的起点，但要接受会存在两个真相之源。

只要两者之间有链接，或者其中一个被声明为真相之源，遗留系统和 markdown 优先系统就可以共存。

CLAUDE.md

CLAUDE.md 给 Claude 提供了一名新入职成员所需要的上下文，涵盖约定、命令、架构，以及团队最常犯的错误。过去存在于人们头脑中和 wiki 上的知识，变成了一份智能体在每次会话开始时都会读取的文件，由整个团队维护，每当犯错时都会迭代更新。

如何开始

前置条件

无。

治理考量

技能是一种控制手段，尽管是建议性的。它让 Claude 在编写代码时更可能应用策略，但没有任何东西强制某个会话遵守它。一条必须始终成立的策略，需要技能背后有确定性的机制，例如阻止该动作的钩子，或是在 PR 处重新检查策略的评审环节。技能让违规变得罕见，而钩子让违规几乎不可能发生。技能调用记录在会话轨迹中，策略负责人像评审代码一样评审技能的修改。

如何衡量

先行指标：从策略负责人批准一项策略变更，到更新后的技能合并的时间（取自技能文件夹上的 PR）。

滞后指标：引用该策略的 PR 评审结论，一旦技能在编写代码时应用了策略，这些结论就应趋近于零。如果结论没有趋近于零，那么要么技能没有触发，要么它的文本已经偏离了官方策略。

钩子作为构建期护栏

技能是建议性的控制手段，而钩子（hook）是它背后确定性的那一层。Claude 在实现期间的大部分动作都是文件编辑和 shell 命令，所以构建阶段是钩子最可能频繁触发的地方。

构建期钩子可以：

  • 阻止对受保护路径的编辑，例如生成的类或冻结的包；
  • 在文件编辑后运行格式化器和 linter，使偏离永不累积；
  • 让凭据不进入 diff。

为任何其策略必须无例外成立的技能提供支撑。钩子会对每个匹配它的动作运行，所以构建期钩子应该快速，并限定在发生变更的文件上。诸如完整测试套件这样的更重检查，属于提交或 PR 阶段。

一个向人类征求批准的钩子，属于阶段 5：部署中的关卡，因为构建期间的批准提示会把一个人重新放回到所有并行运行会话的关键路径上。

并行会话与子智能体

一名工程师可以同时驱动多条工作流。

并行会话是另一个完整的 Claude Code 实例，在自己的git 工作树中处理一项独立任务。每个独立会话对彼此一无所知，指挥它们的工程师是它们之间唯一共享的东西。

一个子智能体（subagent）在单个会话内作为一个受限的助手运行，拥有自己的上下文窗口和工具限制，适合那些在多个任务中反复出现的作业，例如验证应用是否按预期运行。

并行会话提高了工程师可以同时在飞的并发任务数，而子智能体让每个会话专注于自己的任务。工程师的工作是指挥并评审所有这些工作。

传统

一名工程师一次只做一个任务，并把一天或一周中的相当一部分时间花在构建、测试和评审上。等待期间在任务间切换是可能的，但上下文切换累人，以至于很少有人愿意这么做。

AI 原生

一名工程师同时运行几个 Claude 会话，每个都在自己的工作树里、处理自己的任务。重复的作业变成拥有各自上下文和工具限制的子智能体。工程师的工作转向编排，并最终转向构建和监控循环。

如何开始

前置条件

CLAUDE.md，因为所有会话都会读取这份文件。反馈回路（阶段 4：测试）在这里也有帮助，因为当一个会话能验证自己的工作时，所需的工程师监督就更少。

基础设施

一个 git 仓库，因为隔离来自工作树；权限设置经过调优，使会话不会因为组织认为安全的命令而等待批准提示。

如何执行

  1. 工程师使用计划模式行动（阶段 3：构建）中的计划，把工作拆成触及不同文件的任务，从而看清哪里是独立的。共享文件的任务在同一个会话中一个接一个地运行。
  2. 每个并行任务都有自己的工作树，例如在一个终端里运行 claude --worktree feature-auth，在另一个终端里运行 claude --worktree fix-rate-limit。工作树是在自己分支上的独立检出，能防止会话在文件上相互冲突。
  3. 两到三个会话是一个合理的起点。实际的上限是一个人能好好评审多少条流，所以只有在评审跟得上的情况下才增加会话。
  4. 把重复的作业变成子智能体，按 .claude/agents/ 中的 markdown 文件定义，每个都有名称、何时使用的描述，以及它可以接触的工具。示例包括：一个在主智能体完成后剔除不必要复杂度的代码简化器、一个运行应用并检查行为的验证器、一个探索代码库而不淹没主上下文的调研者。把这些定义检入 git，让整个团队共享它们。

04测试（Test）

每个会话都会在人类看到结果之前检查自己的工作，而指挥智能体的配置会像它写出的代码一样得到回归测试。

给 Claude 一个反馈回路

始终给 Claude 一种验证自己工作的方法，无论是测试、构建还是截图对比。一个会话会在工程师看到问题之前检查自己的工作并修复自己的错误。

不要把反馈回路与验证器子智能体（阶段 3：构建）混淆。反馈回路会在整个任务中与工作本身一样多次地运行。而验证器子智能体，则是把最终检查打包的一种方式——一旦会话认为工作完成了，就用一个全新的上下文窗口来运行它。这样，结论就不会被产生那段代码的假设所左右。

传统

表明代码能工作的信号来得很晚。CI 要几分钟，测试者要几天，生产环境要几周。当智能体产出代码时，一个迟到的信号意味着一个人必须检查它的全部产出，而这个人就成了瓶颈。

AI 原生

会话在一个人看到结果之前就获得检查自己工作的方式。运行测试、运行构建、截图。Claude 一直迭代到检查通过为止，所以到达工程师手里的东西已经通过了检查。搭建这个回路是运行会话的工程师的责任，下面的步骤就是为他们写的。

如何开始

前置条件

无。

基础设施

一套测试套件和一个构建，各自用一条命令就能在本地运行。对于 UI 工作，让 Claude 能看到结果的方式至关重要——要么是一个浏览器工具，要么是一个通过 MCP 接入的截图工具。

如何执行

  1. 如果今天检查工作需要一串命令和一些环境知识，就把它包装进一个单一目标，例如 make test 或 npm test，失败时以非零退出。
  2. 在 CLAUDE.md 的命令部分，为每条命令列出健康输出的示例。
  3. 陈述一个目标并让它可量化，这样 Claude 就能在不用问你的情况下检查工作，例如："test_status.py 中的所有测试都通过"、"截图与附上的设计稿一致"或"端点在新字段存在时返回 200"。
  4. 对于 bug 修复，先写失败测试。让 Claude 把 bug 复现成一个测试，运行它，并确认它因你预期的原因而失败。提交那个测试。只有到那时，才让 Claude 在不去编辑测试的情况下让它通过，由最后一步中的测试文件钩子来强制这一限制。一个在修复之前就存在、且智能体无法重写的测试，就是 bug 已消除的证据。
  5. 对于 UI 工作，用视觉检查来闭环。给 Claude 一个浏览器或截图工具，给它设计稿，让它迭代。实现、截图、比较、调整。两到三轮是正常的，结果应该每轮都变好。
  6. 把验证变成"完成"的一部分。指令存在于 CLAUDE.md 中。在报告任务完成前运行测试，并展示输出。
  7. 最后，回路本身也需要保护，因为一个修复代码的智能体绝不能削弱对那段代码的检查。一个在修复任务期间阻止编辑测试文件的钩子就能做到这一点。另一种做法是在评审中检查 diff，并拒绝任何触及测试的变更。

如何衡量

先行指标：智能体写出的变更的一次通过 CI 成功率，CI 系统已支持。

滞后指标：每个 PR 的评审时间（来自 PR 元数据），一旦测试捕获了评审者过去要捕获的东西，它就应该下降；以及来自事故追踪器的变更失败率。

CI 中的持续评估（evals）

评估是阶段关卡式 QA 的 AI 原生对应物。在实践中，这意味着一套在智能体配置发生任何变化时都会运行的测试套件。当接入一个新模型或重写一个提示词时，评估套件会说明智能体是否仍然以同样的标准完成工作。

这些评估应被视为一套活套件。随着模型改进，曾经有判别力的用例不再有判别力，必须添加来自持续监控中浮现的新用例。

根据用例不同，有些团队可能更愿意按固定节奏离线运行这些评估，而不是每次变更都运行。下面的步骤针对的是持续评估。

如何开始

前置条件

CLAUDE.md 和反馈回路（阶段 4：测试）。

基础设施

能非交互式运行 Claude Code 的 CI，以及一个带预算、用于评估运行的 API 密钥。

如何执行

  1. 平台工程师从近期工作中收集 20 到 50 个真实任务及其预期/被接受的结果。
  2. 把每个任务写成一个评估，即提示词加上定义"可接受"的检查（测试通过、lint 干净、行为不变、策略得到遵循）。
  3. 该套件在 CI 中按计划、并在 CLAUDE.md、技能或钩子的任何变更上非交互式运行，因为那份配置在指挥智能体，值得获得代码所得到的回归测试。
  4. 用结果作为配置变更的关卡。一个让通过率下降的技能变更，在合并之前要被评审。
  5. 每个生产事故都会获得一个评估，由拥有该事故的团队编写，并作为回归测试留在套件中。

05部署（Deploy）

评审在两个方向上都运行，治理在智能体行动时被强制执行。智能体做到生产关卡之前的所有事情，而不做之后任何事。

PR 评审回路中的 AI

Claude 既给出评审也接收评审。它对照组织的策略评审收到的 PR，并处理它自己 PR 上的评审意见。这让工程师能够在他们的 PR 评审中专注于行为，这归结为判断意图与风险。

传统

评审能力是按人类产出来规划的。一个 PR 等待一个评审者通读全部内容，评审质量随评审者的负荷而波动，作者在后面追赶，而积压越积越大。

AI 原生

所有 PR 都获得一组相同的评审环节，结论按严重程度排序。人类的注意力上移一层，转到这个变更是否做了计划打算做的事、风险是否可接受。

如何开始

前置条件

一份来自阶段 3：构建的更新后的 CLAUDE.md 文件；如果评审环节强制执行书面策略，则还需要技能和已定义的子智能体。

基础设施

一个安装了 Claude 集成的仓库，要么是管理员启用的托管式代码评审（Code Review）（研究预览）服务，要么是在你自己 CI 中运行的 claude-code-action，在需要时通过 AWS Bedrock、Google Vertex 或 Microsoft Foundry 进行模型调用（CI/CD 行动涵盖部署选项）。要求代码所有者批准的分支保护策略也值得设置。

如何执行

  1. 托管式代码评审服务是最快的起点。管理员启用它并选择仓库。当你需要控制流水线、或想让 API 调用通过你自己的云协议路由时，就在你自己的 CI 中用 claude-code-action 运行评审（CI/CD 行动涵盖那块管道）。
  2. 技术负责人把评审策略写成仓库根目录的 REVIEW.md，分成组织关心的几个环节：bug 与逻辑错误；安全与漏洞；对照规格（来自需求行动的 spec.md）、实施计划（来自计划模式行动的 plan.md）和设计原则的合规性。REVIEW.md 还定义了什么算"重要"（Important）、什么只是"小事"（Nit），以及什么应该跳过。
  3. 技术负责人设定人类阈值。结论本身不会批准或阻止一个 PR，分支保护仍然要求代码所有者批准。想要依据结论把关合并的平台工程师，可以读取检查运行以机器可读计数发布的严重程度统计。
  4. 当评审者或作者在评审意见上标记 @claude 时，Claude 处理该意见并推送修复。PR 线程同时记录请求与变更。这个修复回路通过 claude-code-action 运行。在托管式服务中，评论 @claude review 会请求一次全新的评审。对于 Claude 自己开的 PR，更进一步，让 Claude 照看 PR 直到合并。团队把回路包装进一个自定义斜杠命令，它清扫 PR 上未解决的评审意见和失败的检查，处理它们并推送修复，直到 PR 变绿、只等代码所有者批准。
  5. 评审结论反馈回 CLAUDE.md。当一次评审第二次标记某个错误时，纠正方法作为那次评审的一部分写进 CLAUDE.md，而且因为评审会读取 CLAUDE.md，该错误从下一个 PR 起就会被捕获。评审还会在某个变更让 CLAUDE.md 过时时加以标记。
  6. 每月一次，技术负责人通过给结论打分来调优这套设置，让评审者改进，并在 REVIEW.md 中限制小事（Nit）的数量。生成的路径和任何 CI 已强制执行的内容被排除在外。
它长什么样（REVIEW.md）
# 评审指令

## 环节
运行三个环节，并给每个结论标记它的环节：
- Bug：逻辑错误、坏掉的边界情况、微妙的回归
- 安全：注入风险、身份验证缺口、日志中的 PII
- 合规：变更与 spec.md、plan.md 及我们的设计原则一致

## 这里的"重要"指什么
把 Important 留给那些会破坏行为、泄露数据或违反策略的结论。
风格和命名是小问题。

## 限制小事
每次评审最多报告五条小问题；其余只给出一个计数总结。

## 不要报告
src/gen/ 下生成的文件，以及任何 CI 已强制执行的内容。

治理考量

职责分离被保留下来，因为写代码的智能体无法批准它。在 REVIEW.md 中的评审策略被应用到所有 PR，结论、修复、评分和批准都记录在 PR 历史中，所以 PR 就是审计记录。批准来自通过分支保护的人类，并以结论为依据。

关于这些控制在生产规模下如何组合，参见在 Anthropic 保护其 AI 原生 SDLC。

如何衡量

先行指标：首次评审的时间，应降到几分钟；以及无需人类触碰分支就解决的评审意见占比（数据直接存储在 git 上）。

滞后指标：合并前捕获的缺陷与漏洞，对比那些逃逸到生产环境的，来自 PR 历史和事故追踪器。

钩子作为审批关卡

构建阶段把钩子用作护栏，在没有人介入的情况下允许或阻止动作（阶段 3：构建）。钩子也可以询问，暂停动作直到某个特定的人批准——这正是发布把关（release gating）所需要的。

这项行动放在阶段 5：部署，因为发布关卡是最清晰的情形，但钩子并不限于部署：它们会在 Claude 行动的任何地方运行。例如，钩子可以在阶段 3：构建期间阻止在没有变更工单的情况下编辑迁移和基础设施，并在阶段 4：测试期间阻止智能体在修复任务中编辑测试文件。

如何开始

前置条件

无。

基础设施

一份变更流程所需的批准清单（书面化）。

如何执行

  1. 工程领导层与变更管理和合规团队一起，列出必须保留的人类审批关卡，例如变更管理签字、发布授权，以及对受保护路径的编辑。
  2. 平台工程师把每个关卡表达成一个钩子：一个在 Claude 行动前运行的脚本，可以允许、询问或阻止。
  3. 团队钩子放在 git 中的 .claude/settings.json，而不可协商的钩子放在由平台或 IT 管理员拥有的托管设置中，单个工程师无法关掉它们。
  4. 一次阻止应该自我解释，所以当一个钩子阻止某个动作时，原因和获得批准的途径会出现在 Claude 的输出中。

从控制的角度，每一行换来了什么：

  • permissions.deny 让密钥不进入智能体的上下文，并阻止通过工具进行的任意网络出口；permissions.allow 预先批准安全的内环，这样拒绝清单不会变成提示疲劳。
  • disableBypassPermissionsMode 加上 allowManagedPermissionRulesOnly 意味着没有任何工程师、项目文件或命令行标志能够放宽规则。
  • sandbox 弥合了权限无法覆盖的缺口。对 WebFetch 的工具级拒绝无法阻止 shell 命令触达网络；OS 级的域名允许清单则直接封死出口。
  • failIfUnavailable 和 allowUnsandboxedCommands 让沙箱成为一道关卡：当沙箱无法初始化时 Claude Code 拒绝启动，而在沙箱内失败的命令也无法在沙箱外重试。
  • credentials 弥合了拒绝规则留下的缺口。permissions.deny 约束 Claude 的文件工具，但一个沙箱化 shell 命令默认仍可能读取 ~/.ssh 或 ~/.aws/credentials；这个块拒绝这些读取，并把命名的密钥从每个沙箱命令的环境中剥离。
  • allowManagedHooksOnly 意味着这项行动中的审批关卡是唯一运行的钩子；本地任何东西都无法添加或替换它们。
  • disableSideloadFlags 和 strictKnownMarketplaces 意味着工程师机器上的每个技能、智能体、钩子和 MCP 服务器都来自组织批准的插件市场，绝不来自家目录。
  • allowManagedMcpServersOnly 让智能体的工具面成为一个由平台团队拥有的允许清单。
  • requiredMinimumVersion 拒绝在低于获批最低版本的版本上启动，因此控制手段由一个组织实际评估过的构建来强制执行。

把上述内容视为一个可以定制的起点，而不是一份照抄的推荐。每一项拒绝都在与能力做权衡，正确的平衡取决于仓库的数据分类。设置参考文档记录了每个键，包括仅托管可用的那些：code.claude.com/docs/en/settings。

滞后指标：在钩子之前和之后，到达生产环境的关卡违规（来自事故追踪器）。

CI/CD 集成与部署

在 CI/CD 流水线内部非交互式地运行 Claude Code，对执行进行沙箱化以便长时间运行的智能体安全运行，通过 MCP 集成暴露部署，并在智能体真正需要之前排练回滚路径。

传统

流水线运行确定性的脚本，任何需要判断力的事情都要等一个人类。例如，分流那个偶发失败的测试、写变更日志，或弄清构建为什么坏了。部署和回滚是由人类在压力下照着操作手册执行。

AI 原生

Claude 在流水线内部为判断类步骤非交互式运行，处在一个带作用域凭据的沙箱中。部署工具通过 MCP 暴露给智能体，因此那个编写并测试了变更的工作流也能交付它、回滚它，并且是在组织为每个环境定义的关卡之内。

如何开始

前置条件

PR 评审回路中的 Claude 和作为审批关卡的钩子，因为关卡必须存在，自动化才能加速任何东西通过它们。

基础设施

一个安装了 claude-code-action 的 CI 平台，或任何能调用 claude -p 的运行器；通过 API、或当流量必须留在组织云协议上时通过 Bedrock、Foundry 或 Vertex 的模型访问；针对部署目标的 MCP 服务器；一个用于智能体作业的、无常驻生产凭据的沙箱配置文件。

如何执行

  1. 平台工程师从只读判断步骤开始。在流水线作业中使用 claude -p 分流一次失败的构建、总结一个偶发失败的测试，或起草变更日志。
  2. 把写步骤加在现有关卡之后，用于诸如修复 lint、更新生成的文档，或通过 @claude 提及处理评审意见之类的作业。智能体写出的任何东西都通过分支保护作为 PR 到达，而智能体没有通往 main 的路。
  3. 执行是沙箱化的。智能体作业运行在容器中，受网络策略约束，使用短期作用域令牌，默认不持有生产凭据。
  4. 通过 MCP 暴露部署。部署、状态和回滚成为工具，按环境限定作用域，因此智能体的部署能力是一个允许清单，而不是一个带凭据的 shell 脚本。
  5. 按环境划分自主层级。在开发环境，智能体自由部署。在生产环境，智能体准备发布，发布经理授权它，一个钩子强制执行生产关卡。暂存环境位于两者之间。
  6. 回滚应该是流水线中排练最多的路径：一条智能体可以运行、并在暂存环境定期演练的单命令。闭环行动（阶段 6：维护）在控制带被突破时会调用这次回滚，所以它必须预先被证明可用。

    claude -p "读取 out/build.log 中的构建日志。找出最可能的原因，
    说明失败看起来是偶发还是真实，并为 PR 线程写一段三行的总结。" >> triage.md

治理考量

治理原则是：智能体可以做到生产关卡之前的一切，并且无法越过它。下面的控制手段强制执行这一原则。

  • 分支保护把智能体写出的任何东西都变成 PR，没有通往 main 的直接路径。
  • 生产部署钩子阻止发布，直到一个具名的发布经理授权它。每次非交互式运行都以智能体自己的身份行动，因此流水线日志把智能体做了什么与触发它的工程师做了什么区分开来。
  • 按环境的权限层级决定智能体在通往关卡的路上可以做多少。
如何衡量

先行指标：无需呼叫人类就完成分流的流水线失败占比（取自 CI/CD 流水线日志）。

滞后指标：DevOps 研究与评估（DORA）指标，CI 系统和部署工具已经在发出这些指标。

06维护（Maintain）

循环闭环了。一个触发器在调用路径上没有人的情况下唤起 Claude，而它所发现的东西以 intent.md 的形式重新进入流水线。

维护与闭环

到目前为止，我们讨论了如何把 Claude 加入 SDLC 流程的每个阶段，每个阶段都需要一个人来启动初始步骤。而这个阶段把焦点转向让 Claude 自主运行，以闭合循环。

例如，一个持续运行的监控智能体，可以在一个 bug 工单被提出之后，创建一个 intent.md，并流经需求、计划、构建、测试和评审各阶段。阶段 6：维护是无人值守（headless）运行的，各阶段之间有一个独立的置信关卡——一个确定性检查或一个对抗性评审智能体——决定上一阶段的产出是继续，还是升级给人类。

传统

维护是一个反应性阶段。所有工单或事故都要等一个人去处理并重启流程。一个凌晨 3 点的告警可能被漏掉，一个工单可能在积压里躺到有人接手为止，而如果先发生了另一场火灾，事后总结的行动可能根本到不了代码库。

AI 原生

一个触发器——例如控制带被突破、一个工单、一条频道消息或一个计划——在路径上没有人的情况下唤起 Claude。Claude 进行诊断，只通过受把关的路径行动，并把它的发现写成 intent.md，然后它流经上面描述的那些阶段。人们对这些工作进行分流和评审，而不再需要启动它。

闭环

一个确定性脚本盯着生产环境，当控制带被突破时唤起 Claude。对一次突破的监控，是理解循环自主运行模式的一个有帮助的例子，而本阶段末尾的 Claude Tag（公开测试版）部分则涵盖通过不同渠道到达的工作。

如何开始

前置条件

Intent.md，它给循环一个结构化的输出用来重启。加速的 Claude PR 评审、作为行动边界的钩子，以及一个 CI/CD 的回滚路径（最高自主层级会调用它）。

基础设施

一个检测脚本可以查询的指标存储（Prometheus、CI 系统的 API 或等价物）、对仓库的读取权限、一种在 CI 中非交互式运行 Claude Code 的方式，或用于一个接收 webhook 的服务的 Agent SDK。

如何执行

  1. 服务所有者或平台工程师挑选一个具有稳定滚动基线的指标，例如 CI 测试失败率、部署后的 5xx 率，或 PR 周期时间。
  2. 他们编写检测脚本，通常是滚动窗口上的均值与标准差，并配合规则（Western Electric 或类似规则），这样控制带既能捕获缓慢漂移也能捕获尖峰。脚本是版本化的、经单元测试的，检测完全保持确定性，不涉及任何模型。
  3. 响应层级定义在版本化的配置中（下面的 bands.yaml）。在 1σ 时脚本只记录；在 2σ 时它只读地唤起 Claude 进行诊断；在 3σ 时 Claude 可以行动，但只能通过开一个进入评审关卡的 PR，或触发一个预先批准的运行手册。
  4. 触发层可以是一个 GitHub 或 GitLab 中的计划工作流、一个来自现有监控栈的 webhook，或网络内的一个 Cron Job。Claude 无状态运行，要么作为 CI 运行器上的非交互步骤，要么作为沙箱容器中的 Agent SDK 服务，而 CI/CD 行动涵盖部署和模型访问选项。因为运行是无状态且非交互的，一个循环可以在没有任何人启动它的情况下开始和结束。
  5. 智能体把它的诊断以阶段 1：规划中的格式写成 intent.md，涵盖异常及其证据、一个拟议结果、受影响的系统，以及任何未决问题。从那里，这条发现像其他任何东西一样流经流水线。
  6. 服务所有者或值班工程师对队列进行分流，把面向产品的发现路由给产品负责人。立即修复、排期，或驳回。驳回会调优控制带并帮助降低噪音。
  7. 当一个修复上线时，为该事故添加一个评估（持续评估行动），以确保这类问题在未来得到保护。

治理考量

层级边界从版本化的配置强制执行，权限和托管设置拒绝生产访问。调用、发现和分流决定都带时间戳记录。一个服务所有者对发现进行分流和批准，产生的变更走正常的 PR 评审关卡，而智能体可以触发的运行手册是预先批准的。

如何衡量

先行指标：从控制带被突破到分流队列中出现 intent.md 的时间，对比旧的事故到事后总结行动的时间。检测脚本的日志带有突破时间戳和事故层级。

滞后指标：成为已合并修复的发现占比（分流队列对比实际 PR 历史），以及同类事故的重复次数——随着修复给评估套件增加用例，这个数字应该下降。

示例

  • 当 CI 测试失败率突破 3σ 时，智能体隔离那个偶发失败的测试或开一个回滚 PR，由评审关卡决定。
  • 当部署后的 5xx 率在窗口内有一个部署的情况下突破 3σ 时，智能体触发现有的回滚流水线。
  • 当 PR 周期时间触发一条漂移规则时，智能体为工程领导层写一份报告，这表明该框架既适用于过程指标，也适用于生产指标。

检测保持确定性。一旦某个控制带被突破，Claude 就会被唤起，而层级决定它可以做什么。

周期性代码库扫描

一次安全扫描是关于一个代码库在特定模型下的、针对某一时刻的陈述，而这两半都会过时：代码每周都在变，而每一代模型都会发现上一代遗漏的漏洞。AI 原生的答案是按计划运行扫描，在调用路径上没有人类，并把发现的东西与对代码库的任何其他变更一样，送过同样的关卡。

Claude Security 是计划扫描的托管形式。连接一个 GitHub 仓库，扫描就在 Anthropic 基础设施上以 Claude Mythos 5 运行，每条发现都在被报告之前得到验证并附上置信评级。建议的补丁在网页版 Claude Code 中评审和应用。组织无需访问模型本身就能获得发现。

传统

安全扫描是一个事件，在发布或审计前发起一次扫描。报告送到一个追踪器，积压靠手工消化，直到下一个事件。其间的代码由 PR 评审捕获到的任何东西来覆盖。

AI 原生

扫描按计划针对每个已连接的仓库运行，使用可用的最强模型，发现内容在任何人读到之前就已验证。每条发现都像一个被突破的控制带那样处理：一个能放进一个 PR 的修复走评审关卡，任何更大的内容变成 intent.md。覆盖率从最后一次运行开始计算，而不是从第一次。

如何开始

前置条件

PR 评审关卡和作为审批关卡的钩子（阶段 5：部署），这样发现内容像任何其他变更一样经过评审。对于单个 PR 装不下的发现，使用阶段 1：规划中的 intent.md 格式。

基础设施

Claude Security 向 Claude Enterprise 组织以公开测试版提供。它需要：在目标仓库上安装 Anthropic GitHub App（云托管的 github.com）、启用网页版 Claude Code、开启超额用量（Extra Usage）并设置消费上限、为运行扫描的人提供高级席位，并由管理员在 claude.ai/admin-settings/claude-code 开启该功能。扫描按 Mythos 5 费率按用量计费，因此消费上限应与仓库的规模和数量相匹配。

如何执行

  1. 安全负责人连接仓库，并按仓库、服务或团队把它们组织成项目，这样发现的归属从一开始就清晰。
  2. 对最关键仓库运行第一次全量扫描，包括那些已被其他工具或早期模型扫描过的仓库。把第一次扫描当作基线。第一次扫描很可能在被认为是干净的代码中浮现发现。
  3. 为每个项目设置计划。对积极开发的服务，每周是一个合理的默认值；在仓库很大或混合的情况下，把扫描限定到某个目录或分支。
  4. 手持置信评级对发现进行分流。带理由地驳回，这样驳回会被记录，同一条发现也不会在下一次运行中作为新的返回。
  5. 对于有边界的发现，在网页版 Claude Code 中打开建议补丁、评审它，并像任何其他变更一样送过 PR 评审关卡。提出修复的智能体没有批准它的路。
  6. 对于任何比单个补丁更广的东西——例如一个架构弱点或一个跨服务重复的模式——用阶段 1 的格式把它写成 intent.md，并从规划阶段开始。
  7. 当一个修复发布到生产时，把该漏洞类别的一个评估加到持续评估行动的套件中，这样指挥智能体的配置从那时起就针对那一类进行测试。
  8. 把发现导出为 CSV 或 Markdown，或使用 webhook，让组织现有的追踪器和审计系统保持为审计者已经期待的系统记录。

治理考量

扫描在组织的管理控制下运行，意味着连接哪些仓库、谁持有扫描席位、消费上限是多少，都由中央设置。每条发现都有一个验证结果和一个置信评级，每次驳回都有理由，因此扫描历史就是一份关于发现了什么、修复了什么、有意识地接受了什么的审计记录。

修复通过 PR 评审关卡和分支保护到达生产，而不是来自扫描本身。Claude Security 是对现有静态分析和依赖扫描的补充。确定性检查留在 CI，而模型驱动的扫描覆盖那些检查并非为找出而构建的、依赖上下文的漏洞。

如何衡量

先行指标：处于计划中的已连接仓库占比，以及从一条发现被报告到其补丁进入 PR 评审关卡的时间（从扫描历史和 PR 元数据读取）。

滞后指标：计划扫描发现的漏洞，对比在生产中发现或由外部报告发现的，来自事故追踪器；以及在经历了多轮运行的仓库上，每次扫描发现数的趋势——随着修复和评估的累积，它应该下降。

用 Claude Tag 做 on-call

事故也可以通过其他方式到达，例如 Slack 或 Teams 这类工作场所通讯应用。事故可能看起来像 10 点在一个事故频道里要求紧急修复的一条 Slack 消息，而现在可以立即采取行动。Claude Tag（目前在 Slack 中提供公开测试版）让 Claude 以自己的身份成为这些频道的成员，因此每条新事故都有一个第一响应者，而响应本身成为未来事故的循环与记忆的一部分。

对话和机构知识留在频道里，频道中的任何人都可以引导并执行响应。任何团队成员都可以实时测试假设、探索新选项和进行调查，频道历史增加了可审计性。通过访问 MCP，Claude 验证指标回到基线并在线程中确认它，把事后总结写进一个版本化的经验教训文件，供未来的调查阅读。

事故并不是 Claude Tag 接手的唯一工作。在工单上通过 MCP 标记它，或在频道里提问它，Claude 都以同样的方式分流工作。一个小的、边界清晰的小修复作为 PR 通过评审关卡到达，任何更大的内容被写成 intent.md 交给阶段 1：规划，此时循环开始自我供给。参见：Claude Tag 如何在 Anthropic 为 CI/CD 做 on-call。
