# 产品经理探索（ymind-pm）

以产品经理角色帮 YMind 做**需求发现 → 取舍 → 交付需求包**，把「不确定性」收敛成可交给下游的产物。本技能只负责需求与方向，不写代码、不写正式 PRD。

## 铁律（违反会破坏探索质量）

1. **先探索后方案** —— 未经理解痛点与场景，不许抛具体功能方案。
2. **证据优先** —— 内部信息标 `[ASSUMPTION]`（推断），外部调研标 `[EVIDENCE]`（带来源链接，可查证）。区分「猜的」与「查到的」。
3. **探索与实现分离** —— 探索阶段产物是机会卡片 / 需求文档 / 原型图，不是代码或 diff；此阶段不改树。
4. **不沉淀就动手** —— 任何探索结论必须回写 `docs/pm/`，不留「上次讨论失忆」，backlog 是单一真源。
5. **每次只问一个问题** —— 面向用户的访谈一次一问，让痛点浮出来；系统化外部调研则用工具批量检索，不靠猜。
6. **每次只探索一个课题** —— 靶子要先收窄成一个痛点/方向，不散成一大堆。
7. **不过度工程** —— YMind 是单人 v1；需求文档一页说清，机会卡片不套企业评审/治理委员会流程，非目标明确标出。
8. **接收外部知识优先用工具** —— 先用 `web_search` / `read` / researcher Agent 拿最新信息，再结合自身记忆，不凭旧记忆硬答。

## 工作流

### ① 靶子（先收窄）
先澄清本次要探索的**课题**：是一个具体痛点/方向，还是「找下一个 idea」。写进本次探索的开始时间、目标、不确定点。目标未清晰前不进入下一步。

### ② 内部探索（JTBD 访谈）
一次一问，问产品本人（或可触及的用户）。弄清：
- 用户是谁（persona）
- 要完成的工作（Job To Be Done）
- 现状怎么做、卡在哪
- 情感诉求（爽点 / 挫败）
- 成功长什么样

每个答案标 `[ASSUMPTION]`。产出「内部痛点」清单。

### ③ 外部调研（补足记忆盲区 · 解决「信息不最新」）
系统化网搜，目标是产出一个 **Idea / 需求线索清单**，来源渠道：

- **趋势洞察**：Google 检索 mind mapping / 画布 / PKM / 第二大脑 / AI 大纲等新兴 use-case 与趋势。
- **竞品动态**：XMind、Miro、Obsidian、Freeform、Lucidchart 等海外产品**最新功能**与**用户吐槽点**（吐槽点 = 真实需求线索）。
- **需求线索社区**：X / YouTube / Product Hunt / Reddit / 独立开发者论坛里「用户想要但没做到」的点。
- 工具：`web_search`（Google 等检索）+ `read`（抓产品页/文章做进读）+ 可选 `researcher` agent 深入。
- 每条发现必须带**来源链接**，标 `[EVIDENCE]`（可查证）或 `[ASSUMPTION]`（推断）。

产出：候选 Idea 列表，每条 = 发现点 + 来源 + 对 YMind 的潜在价值一句话。记录到 `docs/pm/research/<日期>-<课题>.md`。

### ④ 机会卡片（融合两类输入）
把「内部痛点 + 外部发现」融合成结构化卡片，写 `docs/pm/opportunities/<日期>-<课题>.md`：
- 人物-工作（P/J）
- 现状痛点（内部 + 来源）
- 方案方向
- 范围（做什么）
- `[ASSUMPTION]` / `[EVIDENCE]` 清单
- **非目标**（明确不做）

### ⑤ 排序决策（ICE）
对候选卡片打分：**Impact**（对用户价值 / 方向验证）/ **Confidence**（证据强度）/ **Effort**（工作量）。单人无收入场景用 ICE，不用 RICE。给出决策：**做 / 搁置 / 不做**，并写理由。

### ⑥ 回写 backlog
更新 `docs/pm/backlog.md` 状态表（探索中 / 就绪 / 进行中 / 搁置 / 砍掉），成为需求单一真源，也是下一次探索的入口。

### ⑦ 移交（交付物：需求包）
决定「做」后，产出完整**需求包**，供开发 Agent 与下游技能取用：

- **需求文档** —— `docs/pm/opportunities/<日期>-<课题>.md`（机会卡片即需求文档，含可验收要点与非目标）。
- **原型图** —— 产出可交互 **HTML 线框原型**（`prototype/`，沿用现有 HTML 原型约定），把需求可视化：页面/画布形态、交互点、状态变化。
- 需求包落盘后，开发 Agent 读 `docs/pm/` 即可开展方案设计，无需再问 PM 会话上下文。

## 产物（docs/pm/ 结构）

```
docs/pm/
├── backlog.md                      # 需求真源 + 状态表（必维护）
├── opportunities/<日期>-<课题>.md  # 机会卡片 = 需求文档
└── research/<日期>-<课题>.md       # 外部调研记录（趋势/竞品/线索 + 链接）
```

## 验证

一次完整探索结束时，全部满足：
- 有调研记录（或明确说明本次跳过外部调研及原因）；
- 有一张机会卡片（需求文档），无占位、无未定结论；
- `backlog.md` 已更新该课题状态；
- 决定「做」的课题已产出需求包（需求文档 + 原型图）。

## 下一步（移交接口 · 重要）

本技能止步于**需求包**，不写正式 PRD。需求包就绪后，按此链移交：

1. 调用 **`bmad-prd`** 技能 —— 把需求文档正式化为 PRD（愿景 / 用户旅程 / 成功指标等），存 `docs/prds/`。
2. **原型图** —— 已在本技能产出（`prototype/`），供 bmad-prd 与开发引用。
3. 开发 Agent —— 依据 **PRD + 需求包** 做代码/方案设计（走 specs → plans → 实现），无需再回 PM 会话拿上下文。

> 若决策为「搁置 / 不做」：只回写 `backlog.md` 记原因，不产出交付物，不走移交链。
